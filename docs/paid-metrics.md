# Paid metric imports and source health (T12)

The manager's **Paid performance** workspace uses authenticated Convex operations and the shared HTTP report adapter. It inspects approved placement mappings, paid impressions and total link clicks, exact daily coverage, import outcomes and source monitoring. Imported values and transport success do not authorize scores, finalization or advertising writes.

## Authority and reporting scopes

`recordTrustedPaidEnrollment` binds nonprofit/campaign, provider, advertiser account, provider campaign/ad, platform, approved entry/version, unchanged media digest, destination and grant revision. External-ad enrollment approval is distinct from object discovery. Only the current nonprofit campaign manager can map an enrollment, retire its future monitoring or request an import; a platform administrator's general campaign read access does not grant these manager-owned actions.

Enrollment contains explicitly attested canonical reporting days. Mapping materializes every such day immediately; the absence of a separate manager registration cannot conceal a missing required metric. `appendTrustedPaidPeriods` adds newly attested exact days to the unchanged mapping without rewriting the original proof or prior required days. Retirement/reactivation affects transport monitoring, not these immutable historical reporting requirements. A placement cannot be reassigned to another entry/campaign, including after retirement.

`paidInputProjection` returns required placement/platform/metric/day scopes, accepted observations and correction history, missing reasons and controlled-evidence provenance. `paidWindowProjection` enumerates a contiguous Chicago competition window, including DST and clipped campaign boundaries, then sums each canonical day once. Missing days remain explicit holds. A weekly/window response does not add a second overlapping report snapshot. Wholly missing subtotals are null; partially observed subtotals are labelled as partial. Known zero needs affirmative trusted proof for that exact metric/placement/day. Confirmed Stripe fundraising remains separate T10/T11 authority.

## Observations, coverage and operations

Each source report contribution is an exact canonical period/placement/metric snapshot with a monotonic source revision and source data-as-of. Corrections append immutable observations; aggregators use one latest accepted observation rather than adding successive cumulative snapshots. Conflicting replay, overlapping/duplicate placement rows, unsafe/noninteger/negative counts, foreign source/account/campaign/creative/grant/destination and integer overflow are rejected. Later incomplete/unknown reads retain previously accepted facts while making current coverage incomplete. Valid known partial values remain visible without claiming completeness; raw normalized rows remain in the operation journal when a source timestamp is unknown.

Report-operation success requires all required transport, authorization, pages and processing to complete. It can coexist with missing period coverage. Source last success, source data-as-of and reporting delay are separate. The owned selected evidence contract uses a **900,000ms freshness budget**; this is a declared controlled-test contract, not an actual Meta/TikTok freshness guarantee. Production freshness and completeness contracts remain held under #12.

Complete coverage schedules a durable expiry at the exact source-time freshness boundary. The expiry compares the current operation identity before marking the stored scope stale, so an older timer cannot invalidate fresh proof. The typed projection distinguishes the latest read's source timestamp/delay from retained accepted observations; unknown or failed latest reads show unknown current delay while preserving the original value and its own timestamp.

Import generations fence slower/reordered concurrent reads and changed authority/mapping inputs. Exact completion fingerprints normalize row order. Queued/reading operations have durable leases and watchdogs; a lost reader becomes failed/superseded after restart without asserting success. Backoff persists across UI requests and restart. The owned selected report contract supports at most 100 distinct filtered ads per operation and 100 pages; exceeding the ad bound records a held/failed operation before a provider request. Production batching needs an approved source contract.

Monitoring starts on first required placement use, before any success, and persists its activation, due check and generations. At exactly 300,000ms from activation or last success no outage opens; at 300,001ms the same scheduler logic opens one manager-only T08 import-outage incident. Successful unchanged imports recover once; successful incomplete-coverage imports recover transport health while leaving the coverage hold. Deactivation retains source/incident history and does not invent a success. The UI displays “No successful import yet” when appropriate. Email states come from T08's durable outbox; queued, failed or unknown email is never described as sent.

## Public provider documentation checked 2026-11-12

These are candidate schema pointers, not account acceptance evidence:

- Meta's [Marketing API Insights](https://developers.facebook.com/docs/marketing-api/insights/), [breakdowns](https://developers.facebook.com/docs/marketing-api/insights/breakdowns/), [Graph results/pagination](https://developers.facebook.com/docs/graph-api/results/) and [Marketing API rate limits](https://developers.facebook.com/docs/marketing-api/overview/rate-limiting/) returned HTTP 429 in this investigation. Their contents were not treated as verified current contracts. Facebook Page Insights is deliberately excluded: page/post reporting cannot establish qualified paid-ad metrics. The owned Meta peer uses candidate ad/account/campaign/publisher-platform rows with `impressions` and `inline_link_clicks`; their equivalence to the required total link clicks has not been established for an actual account.
- TikTok's official [v2.0 synchronous report](https://business-api.tiktok.com/portal/docs/run-a-synchronous-report/v2.0) documents advertiser IDs, dimension/metric selection and pagination, warns about the 20,000-ID reporting limit, and discusses advertiser timezone differences. These constraints prevent treating a successful page as exhaustive account coverage. Its [API overview](https://business-api.tiktok.com/portal/docs/api-reference/v2.0) lists the current reporting route and scope.
- The official [v1.3 basic reports](https://business-api.tiktok.com/portal/docs/basic-reports/v1.3) describes ad reporting and states that lifetime queries do not support day/hour dimensions. That version's examples are not silently used as the v2 request contract. The [official TikTok SDK reporting reference](https://github.com/tiktok/tiktok-business-api-sdk/blob/main/python_sdk/docs/ReportingApi.md) also demonstrates that report versions expose materially different parameters.

Engineering inference: provider-shaped fields must be wrapped in a selected, independently validated report/grant/period contract before they can establish scoring completeness. The owned peers therefore add an explicitly synthetic envelope proving exact test run/account/schema/page/revision/time/scope. Those fields are not claimed to exist on the actual provider. The adapter never infers completeness from nonempty rows, receipt time, HTTP success or an assumed advertiser timezone. Missing/suppressed `-` fields stay missing. No provider-supplied pagination URL is followed; the adapter reconstructs requests at its fixed owned origin and rejects redirects, preventing cursor credential leakage.

## Manager fallback and certification (T13)

The same manager workspace supports reasoned fallback and evidence-backed certification for one competition entry, one paid metric and an exact bounded `[start, end)` interval. UTC form fields retain seconds; backend scopes retain millisecond precision and accept non-day boundaries. A save records authenticated manager, server time, source, exact period, inspected prior value (including unknown), replacement value, reason, evidence reference and version. An inspected input fingerprint and history revision reject stale prior values; operation identities deduplicate exact retries. Active overlapping authorities require explicit release before replacement. General administrator read permission does not grant correction writes.

`paidCorrections:inspect`, `paidInputProjection` and `paidWindowProjection` use the same imported metric inputs and replacement resolver. There is no separate manual scoring formula or fundraising authority. A replacement contributes once in place of imported activity. Platform breakdowns remain labelled imported provenance because an entry-level correction does not establish a distribution between platforms. Fallback alone never certifies completeness. Certification establishes completeness for its metric and interval independently of provider freshness, while adjacent dates, other metrics and other entries retain their own missing or stale holds. Actual-provider and finalization gates remain held.

Counts cannot be prorated by elapsed time. An exact subday certification returns its authoritative value for that exact interval; a broader imported daily total cannot establish the remaining activity outside that interval, so the broader corrected total is null and held. Similarly, a multi-day replacement supplies one exact total without inventing daily allocations. The exact interval remains inspectable in the form. An empty correction display day does not establish a placement requirement or imported known zero.

Successful later reports preserve source observations and operation provenance. Complete covering imports replace uncertified fallback once. Exact matching imports retain certification without duplicate totals, including unchanged source-revision reports. Conflicting, partial or ambiguous coarser/unknown-time reports retain certification and append held reconciliation history. A durable `certified-metric-conflict` incident notifies current campaign managers through the existing T08 outbox; delivery, failure, unknown and configuration holds remain distinct. Existing administrator incident inspection policy is unchanged. Explicit manager release retains certification/release history and re-exposes latest retained imported values with completeness re-evaluated. Completion, save and release execute as Convex transactions so concurrent operations revalidate their read inputs.
