# Fundraising confirmation and commission ledger

T10 implements the account-free fundraising flow at `/fundraise/:entryId` and `/fundraise`, through `/api/fundraising` into Convex. Fundraising donations are separate from advertising contributions and never enter the advertising-fund balance. Cross-platform URL parameters cannot replace the path's original entry. Once-approved old links remain usable; withdrawal/removal cutoff history hides their creative while preserving nonprofit support and valid earlier earnings.

The owned verification harness runs an HTTP peer implementing the selected Stripe Checkout/Event/PaymentIntent/Charge wire shape. Every visible checkout and financial record says controlled/unvalidated. It does not contact Stripe, collect card information, send email or authorize money movement. The normal deployment handler provides no owned capability, so checkout is unavailable. Environment variables and browser checkboxes cannot activate it.

## Confirmation and durable boundaries

The scope also pins an opaque SHA-256 transport binding of the exact provider origin and credential identity. An uncertain checkout cannot be retried against another provider/idempotency store or credential configuration, even if account, run and route names are unchanged. Keys themselves are never persisted in the journal or evidence.

Before the provider POST, a Convex transaction journals immutable USD amount, origin/creator, nonprofit, locked rules, account, route, API version, application origin/return paths, operation identity, status capability hash and provider idempotency key. Exact retries retain this identity. Unknown create responses remain uncertain until that same key recovers the original session; unbound callbacks remain held in the meantime. Retrying an unknown write after the conservative 23-hour local retry deadline is held, because Stripe may prune keys after 24 hours. Changed amount, origin, route, configuration or return origin cannot reuse the operation. Redirects from the owned provider are rejected.

The callback verifies original raw bytes, a fresh Stripe-Signature HMAC, exact account/mode/API scope and the independently retrieved event. It retrieves the original Checkout session and expanded PaymentIntent/Charge, then checks their journal references, purpose, nonprofit, amount, USD, successful received funds and full capture. Pending/failure/browser return alone never confirms. An atomic Convex mutation binds one donation to both checkout and account/payment identity, preventing same-event, distinct-event, concurrent and restarted replay duplication. Gross/commission records are immutable. Separate append-only fee observations and cumulative T11 refund corrections reconcile later facts without duplicating original gross or original commission. Unknown fees remain null rather than fabricated zero. Raw-event and normalized-facts hashes remain distinct; actual balance-transaction references bind known fee evidence.

Private manager projections retain financial identity. Creator projections return only their own scoped itemization and exclude financial-provider identity. Guest status requires the random checkout capability and returns only pending/confirmed controlled status. No donor identity, provider secret or administrator capability is exposed by public campaign queries. Current authorization is reevaluated for private reads, including revoked users and another nonprofit.

Commission uses locked basis points on gross whole USD cents, per donation with exact BigInt half-up rounding. Original half-open earning dates and effective withdrawal/removal cutoff determine eligibility. Daily Chicago calendar periods and Monday–Sunday weeks retain their original labels; only complete competition days/weeks wholly within competition dates receive competition-period credit. Earning-only partial/outside competition periods still earn commission. Existing Chicago boundaries handle 23/25-hour days and 167/169-hour weeks.

## Time mapping and production integration hold

Stripe documents `payment_intent.succeeded` as a successful payment transition and event `created` as event creation time. These are **not proof that event creation equals the original payment completion instant for every method/capture/API version**. The owned peer supplies an original success-transition clock; the adapter explicitly labels it `controlled-success-transition-v1`. It reads complete bounded success-event history and holds missing/incomplete history. Duplicate-event ordering never changes an already stored donation. Checkout, PaymentIntent and charge creation, invoice creation/payment attachment, receipt delivery, callback receipt and fee availability are never substituted for real completion time. Post-payment invoices may be produced after payment; their timestamps were investigated and not adopted as a completion-time shortcut.

The production capability producer, release controller, real Stripe account credentials/transport binding and actual successful-payment-time resolver remain unwired and fail closed. T10 owns the implemented journal, wire request/confirmation engine, immutable scoped settlement, ledger and shared application views. Before connecting real collection, #20/#21 must supply independently reviewed fundraiser-specific program/account eligibility; beneficiary, purpose, source/destination and collection/refund route acceptance; supported payment method/capture/API scope; amount/fee/refund evidence semantics; and a demonstrated original-success timestamp mapping, including delayed and capture behavior. T40 must verify that those exact reviewed capabilities are bound to the production transport and Convex gate with scope/configuration/freshness revalidation. Actual binding remains blocked pending #20/#21 facts and must be completed before release. Advertising crowdfunding approvals do not authorize this purpose. No implementation here claims those prerequisites are met, and synthetic records must never be promoted to production donations.

## Primary Stripe contract references (read 2026-11-12)

- [Checkout creation](https://docs.stripe.com/api/checkout/sessions/create): form-encoded Checkout requests and parameter shape; [Checkout object](https://docs.stripe.com/api/checkout/sessions/object): session identity, amount, mode, status and related PaymentIntent.
- [Fulfillment](https://docs.stripe.com/checkout/fulfillment): retrieve payment status, support asynchronous success, and settle at most once under concurrent calls; browser redirects are insufficient proof.
- [Webhooks](https://docs.stripe.com/webhooks): raw signatures, timestamp freshness, duplicates and unordered delivery; [event object](https://docs.stripe.com/api/events/object) and [event types](https://docs.stripe.com/api/events/types): event scope/version and success transition meaning.
- [Event listing](https://docs.stripe.com/api/events/list): versioned event history has limited retention; [idempotent requests](https://docs.stripe.com/api/idempotent_requests): stable keys retain original results and parameter identity, with finite retention.
- [PaymentIntent](https://docs.stripe.com/api/payment_intents/object), [charge](https://docs.stripe.com/api/charges/object), [balance transaction](https://docs.stripe.com/api/balance_transactions/object): received/captured gross, refund/fee identity and separate availability semantics. The selected USD card route accepts 50–99,999,999 cents.
- [Receipts/post-payment invoices](https://docs.stripe.com/receipts), [InvoicePayment](https://docs.stripe.com/api/invoice-payment/object) and [invoice attachment](https://docs.stripe.com/api/invoices/attach_payment): invoice payment transitions do not establish a universal earlier PaymentIntent completion timestamp.
- [API versioning](https://docs.stripe.com/api/versioning): current pinned wire version `2026-10-28.endive`.

## T11 cumulative refunds and protected corrections

The shared callback now accepts verified `refund.created`, `refund.updated`, `refund.failed` and `charge.refunded` observations in addition to original Checkout success. It independently retrieves the event, original session/payment/charge and the complete charge-filtered Refund list, then retrieves each refund object. Exact account, API version, test mode, transport binding, original journal, USD, amount and object relationships remain required. No refund-creation, transfer, payout or bank endpoint is implemented. A refund callback received before original donation confirmation is retained against the original checkout; it cannot manufacture successful donation recognition.

Only accepted canonical `succeeded` refund objects reduce principal. `pending`, `requires_action`, `failed` and `canceled` observations do not establish refunded principal. The charge aggregate is checked for valid cents but is never the authority for commission reduction. The bounded selected read contract requires `has_more: false` for at most 100 refund records. Larger, missing or incomplete history holds for reconciliation; it is not silently interpreted as zero. This is a conservative controlled contract, not a claim that Stripe provides atomic list/object snapshots or a universal refund completion clock.

A signed Convex receipt allocates an increasing read generation before canonical refund-history reads. A slower read cannot overwrite a newer generation. Each completed generation binds its raw-event digest separately from the normalized retrieved-facts digest and retained outcome. Exact completion replay is idempotent; changed completion facts conflict. Append-only observations distinguish accepted financial facts from held evidence. A later failed/canceled/pending observation contradicting a previously accepted success, a success with a failure balance transaction, or missing retained history leaves the previously recognized amount intact and opens one manager review incident. A complete coherent fresh read can resolve the held incident, with retained observation and recovery history. No automatic restoration is inferred from a failure balance transaction. Any actual returned-funds restoration contract remains an explicit #20/#21 verification prerequisite.

Original donation gross, original commission, successful-payment time, origin, locked rate/rules, eligibility and Chicago periods are immutable. Corrections append cumulative refunded principal, remaining eligible gross, current recognized commission and the signed difference from prior recognized commission. Whole-cent BigInt half-up rounding is applied to remaining eligible principal, never to each refund delta. Principal cannot exceed original gross; cumulative commission reversal cannot exceed original commission; all signed aggregates reject unsafe integers. The private ledger labels original commission separately from current recognized commission and reversal. Unknown/retained original processing fees remain independent from principal and commission.

Commission balance is corrected recognized commission minus immutable confirmed-paid commission in the exact nonprofit/campaign/creator/account/route scope. A paid6c commission followed by corrected5c earnings yields a -1c carryforward. Future3c commission leaves 2c payable; refunding that future credit restores the prior negative balance. The balance never reads or nets fixed prizes, advertising funds, another scope, or a bank account. Negative balance creates a manager review incident. There is no browser mark-paid operation.

`recordTrustedCommissionObligation` and `recordTrustedCommissionPayment` are nonregistered trusted backend integration seams. The actual payout owner must supply an independently approved immutable obligation identity, beneficiary, USD amount, source, permitted destination binding and revision, with approval actor/evidence/version; the confirmed-payment producer must verify exact correspondence and provide distinct confirmation actor/source/evidence and actual confirmed time. Approved, pending and unknown are not paid. These seams retain facts of already confirmed commission payments and do not approve or initiate payment. The run-owned copied fixture controls are never registered in application deployments and cannot establish actual payout authority.

`fundraisingPeriodResults` persists original and corrected FUNDRAISING inputs/results for the original daily/weekly periods. It fabricates no impressions, other metrics, total score, rank or prize. The nonregistered `recordTrustedFundraisingPeriod` seam validates referenced donations against the exact entry/nonprofit/campaign/period and is shared by refund, later import and certified/manual-correction producers. Those future owners must validate their own authoritative source before invoking it. `recordTrustedFinalizedFundraising` observes an immutable already-finalized result/winner/fixed-prize obligation supplied and verified by the actual scoring/finalization owner. It never awards or pays a prize. Whether source correction precedes or follows this historical snapshot, original finalized facts are preserved and a separate discrepancy plus durable manager notice is appended. REQ-136/137 owners retain exceptional correction and paid-prize-loss policy.

The new manager-only incident kinds are `fundraising-discrepancy`, `commission-overpayment` and `fundraising-refund-held`. Explicit routing preserves all fourteen preexisting kinds and avoids positional kind-policy changes. Current manager role and verified contacts govern delivery through the existing T08 outbox; notices remain visible if configuration or email delivery fails. Repeat observations update the unresolved incident without duplicate detection mail. Creator projections omit payment/charge/account/refund identity, beneficiary/destination bindings, winner identity and private delivery details.

### Primary refund references (read 2026-11-12)

- [Refund object](https://docs.stripe.com/api/refunds/object): refund identity, amount, original charge/payment links and five statuses; `created` means object creation, and `failure_balance_transaction` describes reversal of the initial balance impact after failure. The implemented conservative hold for contradictory success/failure is an engineering inference, pending actual route validation.
- [Refund listing](https://docs.stripe.com/api/refunds/list): charge filtering, 1–100 page limit and cursor pagination. The charge's default ten recent refunds are insufficient proof of complete history; this adapter holds when bounded history is incomplete rather than inferring financial totals.
- [Refunds](https://docs.stripe.com/refunds): partial refunds, pending/failure/cancellation and retained original processing fees. Request submission is distinct from a successful refund.
- [Events](https://docs.stripe.com/api/events/object) and [webhooks](https://docs.stripe.com/webhooks): versioned provider observations, raw signatures, limited event retention, unordered/duplicate delivery; event or callback receipt order is not financial authority.
