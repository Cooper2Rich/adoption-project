# Stripe delayed payments and Clerk access: research brief

Research date: 2026-11-07. This brief explains the provider documentation for the adoption.is launch. It is not account-specific validation or a change to the accepted product rules. Provider pages are linked for details and configuration-specific behavior.

## Stripe: what a delayed payment means

Some payment methods do not confirm the payment immediately when a donor completes Checkout. For example, a bank debit may need subsequent confirmation. The donor completing the form and returning to the website means the Checkout flow reached a completion point; it does not necessarily mean a delayed payment has succeeded. Stripe communicates subsequent changes to your server through events. Stripe describes the relevant Checkout event types in its [Checkout payment events guide](https://docs.stripe.com/payments/existing-customers?platform=web&ui=stripe-hosted) and [event catalog](https://docs.stripe.com/api/events/types). For the campaign, a pending payment must not be included as confirmed fundraising or generate commission until the integration establishes successful payment under the chosen method and account configuration.

### Example timeline

1. The visitor follows an ad's tracked fundraising link. The application creates a Checkout Session server-side and retains a durable association between that session and the competition entry. Avoid relying on a browser redirect or a client-supplied ad identifier as the only record of attribution.
2. The donor submits payment details. For an immediate method, payment may already be successful when Checkout completes. For an asynchronous method it can remain pending. `checkout.session.completed` reports completion of the session, not a universal guarantee that funds have settled. Check the Session's payment state and the authoritative related payment object before treating it as confirmed. Stripe's [fulfillment guide](https://docs.stripe.com/checkout/fulfillment) describes checking `payment_status` and handling delayed methods.
3. If the delayed payment succeeds, Stripe can send `checkout.session.async_payment_succeeded`. Record confirmed fundraising and the applicable commission once, attached to the original ad and the appropriate business-effective time. If it fails, `checkout.session.async_payment_failed` indicates the delayed attempt failed. Do not count it as confirmed; expose an honest pending/failure state where appropriate and permit a new attempt through the intended flow.
4. Stripe delivers events to a webhook endpoint. The handler verifies the signature using the endpoint's webhook signing secret, acknowledges receipt promptly, and processes reliably. Stripe warns that events can be duplicated and delivered out of order; automatic retries may occur. See [Stripe webhooks](https://docs.stripe.com/webhooks). A redirect can be lost if the donor closes the browser, so it cannot be the sole source of confirmation.
5. Store event identifiers and stable payment/obligation identifiers, and reconcile current Stripe objects when event ordering or delivery is uncertain. Processing both an immediate completion and a later success notification must never count the same payment twice. A replay, worker restart, or webhook retry must not duplicate fundraising or commissions. Signature verification, durable event processing and business-level uniqueness have separate jobs.
6. A payment's success is different from money being available in the Stripe balance, a transfer to a connected account, and a payout from an account to its bank. Each has its own state and timing. Stripe's [Connect charges and transfers](https://docs.stripe.com/connect/separate-charges-and-transfers) describes one possible arrangement; the [payout API](https://docs.stripe.com/api/payouts/create) describes payouts to an account's own bank account. Neither proves which arrangement adoption.is is eligible to use.

### Timing, refunds and corrections

The exact event or object timestamp that should represent the successful-payment instant for every enabled method is not established here. Session creation time, the time a webhook arrives, payment success and balance availability are different concepts. Before assigning donations to Chicago competition periods, validate the authoritative timestamp and behavior for each enabled method, including an initiation before midnight and success after midnight, daylight-saving changes, retries and out-of-order events. Do not silently substitute webhook arrival time. The already-agreed 48-hour finalization rule does not guarantee that every delayed transaction will succeed within that window; test the selected payment methods and reconcile later events according to the existing finalized-result rules.

Stripe supports full and partial [refunds](https://docs.stripe.com/refunds); depending on method and balance, a refund may be pending or fail. A request to refund is not, by itself, evidence that a refund completed. Record authoritative refund states and cumulative amounts, deduplicate their events, and apply the PRD's per-donation rounding, remaining-amount recalculation and commission adjustment rules. Ordinary refunds do not automatically reopen a finalized prize. Disputes and other later reversals need separate mapping and testing; a successful payment is not an unconditional promise that it can never be reversed.

[Stripe idempotency](https://docs.stripe.com/api/idempotent_requests) helps make retries safe, but its keys are not a permanent business ledger: keys may be removed after at least 24 hours and a repeated key can return a cached result, including an error. Preserve durable local obligations, approval records and Stripe object identifiers. Reconcile an uncertain transfer or payment outcome before trying again; never assume a timeout means the first operation failed.

### Stripe key or token?

For an application operating its own Stripe integration, the normal choice is a **server-side Stripe API key**, preferably a restricted key with the minimum permissions that actually support the required operations. Use separate test and live environments. A publishable key is intended for client-side Stripe components; it is not the credential for sensitive server operations. A webhook signing secret verifies incoming event signatures and is a separate secret from an API key. See [Stripe API keys](https://docs.stripe.com/keys) and [webhook signature verification](https://docs.stripe.com/webhooks/signature).

An OAuth access token is relevant when the application is authorized to access another Stripe account through a supported Connect/OAuth integration. It is not automatically safer or more suitable as a substitute for the application's own server key. The exact connected-account approach depends on the ultimate platform/beneficiary arrangement and Stripe's current Connect model; verify that arrangement first. See [Connect OAuth](https://docs.stripe.com/connect/oauth-reference). Keep all secret credentials on the server, restrict and rotate them, and never put them in source control or a browser. No credentials are needed to make the product decision now.

## Clerk: invitations, magic links, keys and tokens

### The important distinction

Your intuition is right that Clerk supports email magic links for passwordless signup and sign-in. Clerk calls them **email verification links**. A person starts a sign-in or signup, Clerk sends an email, and opening the link advances the verification or authentication flow. The documented email link expires after 10 minutes. Clerk can require the same device and browser that initiated the flow; this protection is enabled by default and prevents a specific cross-device attack, but means someone starting on a laptop cannot simply complete that same flow by opening the link on a phone when the restriction is on. See [sign-in options](https://clerk.com/docs/guides/configure/auth-strategies/sign-up-sign-in-options) and [email-link protection](https://clerk.com/docs/guides/secure/best-practices/protect-email-links).

A **Clerk application invitation** is a separate mechanism. The manager creates an invitation for an email address; Clerk sends a unique invitation link; when visited, Clerk redirects to signup and automatically verifies that invited email. Clerk says invitations normally expire after a month, and an expired link falls back to the normal signup flow without automatic verification. Ordinary invitations by themselves do not make the entire application invite-only. See [Clerk invitations](https://clerk.com/docs/guides/users/inviting).

The distinction matters for forwarding: the invitation link is documented to preverify the address when visited. The email-link same-device protection is documented for initiated sign-in/signup verification flows; the documentation reviewed does **not** establish that turning it on forces a separate mailbox-ownership check after an invitation link has been forwarded. Consequently, we cannot yet promise the PRD's forwarded-invitation denial from configuration alone. Test actual behavior in an isolated Clerk instance, including a forwarded first-use invitation, existing user, expiry, replay, and whether the intended magic-link step independently proves control of the invited mailbox before private campaign access. If Clerk offers a supported combination that does this, use it; do not invent an internal recovery system or prematurely change the product requirement.

For restricting signup, Clerk documents an [invite-only access mode](https://clerk.com/docs/guides/secure/restricting-access). Configure it if consistent with the application's account needs, and separately enforce server-side campaign membership and creator authorization. An authenticated session does not by itself establish that a person is the right creator for every private record. Revoking an invitation and revoking a previously authenticated user's campaign access are different operations; test active sessions and direct requests after removal. Clerk's [invitation revocation](https://clerk.com/docs/reference/backend/invitations/revoke-invitation) describes the invitation operation.

### Clerk key or token?

Use **both, for different purposes**. The Clerk publishable key configures client-side Clerk components. The Clerk secret key belongs on the server and authenticates server-side calls to Clerk's Backend API, such as creating invitations. The secret must never be exposed to the browser. Clerk's [terminology guide](https://clerk.com/docs/guides/development/sdk-development/terminology) distinguishes both keys and its backend and frontend APIs.

A **session token** identifies an authenticated user's session to the application backend. The backend verifies it and then authorizes the requested action. It is not a replacement for the application's secret key when the server needs to call Clerk's Backend API. For same-origin calls Clerk normally carries the session token in a cookie; cross-origin calls may need it in an Authorization bearer header. See [Clerk authenticated requests](https://clerk.com/docs/guides/development/making-requests). Other Clerk token types, including machine-to-machine and sign-in tokens, solve different problems and should not be conflated with either the Backend API key or the user's session.

### Recovery and operational checks

Use Clerk-supported recovery. For users with MFA, Clerk documents recovery options including backup codes and, depending on configuration, passkeys; an MFA reset through supported administrative mechanisms has its own identity-verification and session implications. See [Clerk MFA recovery](https://clerk.com/docs/guides/secure/mfa-recovery). Test loss of the sole manager's authentication factors and separately establish the recovery path for the Clerk Dashboard and mailbox: the cited guidance does not prove those separate accounts can always be recovered. Also test invitation expiry, replay, verified-email changes, revocation with an active session and isolation between creators. No provider account was accessed for this research.
