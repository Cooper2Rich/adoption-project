# Operator incidents and email delivery (T08)

The durable incident is independent of delivery. `recordTrustedIncident` is a backend-only producer seam; future import, media, prize, batch, finance, capacity, delivery, evaluation and launch monitors must validate their own evidence and call it in their transaction. There is no public observation mutation. S1 allocation previews remain synthetic and never enqueue these emails. This ticket supplies infrastructure and controlled coverage of every route, not live monitoring coverage or provider approval.

A stream is campaign + stable problem key, bound to one producer/category. A strictly newer sequence and nondecreasing observation time are required. A current problem updates one open incident; recovery resolves only that episode and creates one recovery notice. Reopening creates a new incident/notice episode. Original detection, first observation, original evidence, producer and all accepted actor/source/time/version observations remain. A stale recovery cannot resolve newer evidence.

Import outages, prize replenishment, batch readiness, public-media outages and prize losses notify managers. Capacity waiting, failed/uncertain stopping, unavailable delivery, interrupted evaluation, pause-reserved slots, financial safety pauses, insufficient initial trial coverage and launch blockers also notify all active platform administrators, including the configured designated operator. There is no intentional grace delay in this layer. Import liveness thresholds and sampling belong to later trusted producers. Subjects and normalized identical addresses deduplicate; each HTTP message has one recipient and no CC/BCC. Current nonprofit membership/operator authority and exact verified contact are rechecked at dispatch/retry. Missing configuration remains visible while available authorized recipients receive their notices.

Each person registers only their own email from the verified Clerk identity claim. Arbitrary caller-supplied addresses are not accepted. Designation requires an existing active `operators` identity. Contact/designation/resume changes retain scope, actor, source, time and version audit. Signed manager/admin public operations enforce current access; creators, guests, revoked managers and other nonprofits are denied. Private email addresses, provider IDs, credentials, immutable payloads and provider-binding digests are excluded from the dashboard projection. Trusted evidence/reasons must be bounded, operator-safe descriptions and opaque references, never credentials, raw provider responses or creator-private payloads.

Detection atomically commits the incident, immutable notice snapshot, per-person email intents and zero-delay durable jobs. This is immediate durable dispatch intent; the observed time to the journaled first transport is measured in tests, not a promised provider latency. Missing provider approval creates a visible hold. Explicit `resume` rechecks unsent configuration-held notices without replacing uncertain/accepted sends. A resolved incident supersedes unsent detection messages; recovery keeps its own original snapshot. Existing attempted messages are never silently rewritten after configuration/contact changes.

Before a POST the worker commits an immutable attempt with payload, recipient, ordinal/key, provider configuration/credential binding, source, timestamps and transport-call generation. A generation-fenced per-email scheduled mutation commits its next watchdog before enqueueing the at-most-once action. Intent creation, retry and unsent resume atomically schedule that watchdog; a failed action before claim cannot strand the pending intent. Its thirty-second pulses/lease recover worker crashes and stale generations are inert. A stale completion cannot modify a newer transport call/attempt. A confirmed API rejection or retrieved terminal failure schedules a fresh journaled message after successive delays of 1, 5, 15 and 60 minutes from each confirmed failure. Initial send plus four retries yields five attempts; the fifth failure shows exactly **Email delivery failed** while the incident stays open.

Timeout, malformed success, server error and ambiguous conflict remain unknown. A replay rejection (including 401/422/429) proves only that replay failed; an earlier unknown send may already exist, so it stays unknown with zero confirmed failures and never gains a replacement key. They replay only the exact immutable payload/key against the same provider binding within the twenty-four-hour idempotency window. A conservative replay-start cutoff one minute before expiry includes the ten-second transport budget and fifty-second operational margin; cutoff-minus-one permits a loopback replay, while the cutoff and exact expiry both hold for evidence-backed reconciliation. This margin does not guarantee when a remote provider processes a request. The exact expiry boundary holds for manual evidence-backed reconciliation; it never generates a replacement key. A provider account/key/configuration change holds an existing attempt conservatively. Verified same-account credential rotation is a later reconciliation concern. Recipient authority changes also hold rather than leaking to the old address. Provider acceptance is separate from recipient-mail-server acceptance, and neither guarantees inbox placement or reading.

The Resend candidate uses POST `/emails` with `Idempotency-Key`; GET `/emails/{id}` with the bound stable response ID verifies delivery state. Retrieved delivered marks mail-server acceptance; opened/clicked/complained establish later receipt evidence (with the exact event retained), so skipping the delivered event cannot cause replacement sends; bounced/failed/suppressed are confirmed failures; delayed/other pending states stay accepted. Failed retrieval keeps the accepted record pending confirmation. There is no public unsigned callback ingestion. Production requires `RESEND_API_KEY`, `OPERATOR_EMAIL_FROM` and `OPERATOR_EMAIL_REVIEWED_EVIDENCE` JSON containing provider `resend`, a SHA256 evidence digest, HTTPS review URL, named reviewer, exact sender, `verifiedSender: true` and `verifiedClerkContacts: true`. Deployment operators supply reviewed evidence; this format does not itself establish actual capability. No credentials, real addresses, integration or account were provisioned. T39 real email/domain/contact evidence and release approval remain unmet.

Owned fixture campaigns can only use their matching isolated run ID, loopback HTTP transport and reserved `.example` contacts/from. They cannot switch to the production adapter. The fixture mirrors Resend requests and server-side idempotency without external email; its accepted/delivered outcomes are visibly unvalidated. Fixture observation/time controls exist only in the copied local deployment. The Vite development endpoint exposes bounded named scenarios, never production event authority or admin credentials.

Primary provider sources reviewed 2026-11-12:

- [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys): keys last 24 hours, max 256 characters, exact same request replay.
- [Send email API](https://resend.com/docs/api-reference/emails/send-email): POST request and returned message ID.
- [Retrieve sent email](https://resend.com/docs/api-reference/emails/retrieve-email): authenticated GET and `last_event`.
- [Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions): scheduled mutations retry automatically; scheduled actions execute at most once, requiring the separate durable watchdog.
- [Email event types](https://resend.com/docs/webhooks/event-types): accepted/send, delivered, temporary delay and terminal failure distinctions. No webhook authenticity claim is made; this candidate uses authenticated retrieval.
