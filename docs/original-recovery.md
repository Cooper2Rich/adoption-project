# Original deletion and recovery

T07 implements ADR-0002's explicit administrator confirmation and 30 elapsed UTC days of recovery. Exact upload SHA-256/size, linked entry/revision identities, actor, source, time, confirmation and generation remain audited after physical deletion. Playback state is independent.

## Authority and fixed recovery deadline

An active platform operator from the existing `operators` registry types `DELETE ORIGINAL`. Managers and creators can see their permitted archive status but cannot request, restore, reconfirm or retry deletion. Current authority and resource scope are checked before idempotency lookup. Each request fixes `requestedAt + 2,592,000,000ms`; duplicate requests cannot extend it. Restore is accepted strictly before that deadline and before irreversible dispatch. A restored generation defeats stale jobs across restart.

Purge rechecks the confirming operator. Revocation holds dispatch. Another current administrator may explicitly reconfirm an undispatched request with the same typed confirmation. This adds an audit event and changes authority while preserving generation, original request time and deadline. It cannot reopen recovery or reauthorize dispatched/uncertain deletion.

## Current use and atomic write fences

Deletion is blocked while any entry containing this original is approved, including an original in that entry's revision history. Live/uncertain ingestion or an unexpired source lease for this original or that entry's current revision also holds, as do unknown processing states and unresolved entry identity. Reservations and authorized candidates for any linked entry hold, including historical revisions. Unmapped commitment identities, mismatched reservation totals and nonzero unattributed campaign authority commitments conservatively hold all originals in the campaign. Campaign funding alone is not use.

Pending/rejected/revisions entries without ingestion or commitments are not approved publication. Full withdrawal/completion and paid-placement lifecycle APIs remain future slices. Current `photos:submit`, approval in `photos:review`, processing claim/verification in `videos:record`, and `reservations:reserve` read archive fences for the current and historical originals in the same Convex transaction as the use-starting write. Only retained/restored originals can start their own use. Unresolved historical deletion also blocks entry activation; terminal confirmed-deleted historical tombstones permit a different current original to activate. Unmapped reservations read the campaign archive index and cannot start during an unresolved archive intent. Terminal confirmed-deleted originals still deny their own use but permit unrelated reservations.

Future candidate authorization, reactivation and paid-placement writers must use this transactional guard and represent relevant commitments in the current-use check. A read-only check followed by an independent write is insufficient. No new broad lifecycle API is implied here.

## Durable worker and unknown results

The confirmation transaction schedules an internal Convex action at the deadline. It calls the configured application worker with a fresh, signed, purpose-separated job. Read-only preflight validates storage identity, complete size/hash and ETag first. Failures remain undispatched and retryable without changing the deadline. After preflight, the signed claim transaction rechecks generation, exact original, deadline, current authority and current use, then persists dispatch intent and audit immediately before conditional deletion. Revocation during a long read therefore holds deletion. Restore and activation writers serialize with that transaction. Results carry the persisted nonce and generation. Jobs after dispatch perform reconciliation reads only; they never issue replacement deletion calls.

Failed/unknown deletion remains visible and fenced. Presence alone cannot establish that a delayed deletion will never arrive. Only confirmed uncached origin absence transitions to `deleted`; listing absence is never evidence. No uncertain delete is blindly retried, restored, recreated or assigned a reused pathname. A crash between claim and external dispatch deliberately holds the original for reconciliation. Uncertain presence currently stays held; future operational recovery needs conclusive provider evidence before clearing that fence.

## Provider gate and SDK evidence

No real provider action, configuration, provisioning or deployment was performed. Production purge requires `VIDEO_PROVIDER_EVIDENCE_ID`, `ORIGINAL_DELETE_PROVIDER_EVIDENCE_ID`, a Blob read/write credential, and `VERCEL_BLOB_RETRIES=0` in the application worker environment. Convex also needs `VIDEO_ARCHIVE_WORKER_URL` pointing to the trusted HTTPS `/api/videos` endpoint and the same existing `VIDEO_RECEIPT_SECRET`. Missing configuration preserves the request; administrator retry schedules reconciliation after configuration is supplied. Settings are gates, not evidence receipts or approval. T39 supplies actual media evidence; T40 aggregates release proof.

Installed `@vercel/blob` 2.9.0 supports single-object `del(pathname, {ifMatch})` and private `get(..., {useCache:false})`. The adapter streams size/hash before conditional deletion and then checks uncached origin absence. Auth/network failures are errors, not absence. Installed SDK `getRetries` defaults to ten transport retries, with no per-call retry option in `BlobCommandOptions`; requiring the explicit zero environment setting prevents hidden deletion retransmission. No endpoint idempotency guarantee is assumed.

Byte verification pins SHA-256 of the actual private Blob origin to the immutable upload. Records/grants contain this opaque binding, not the origin, credential or raw storage configuration. The server derives the origin from the current read/write token using the installed SDK's store-ID convention, compares the hash before any pinned read, and constructs the full provider URL only on the server. Purge, downloads and ingestion therefore reject a different store before reading or deleting, while token rotation for the same store preserves identity. Requests snapshot that binding too. A scoped signed context read permits read-only preflight before the dispatch claim. Earlier production records without a verified binding keep their bytes but cannot start original downloads, ingestion or purge until an evidence-backed migration establishes it. Existing processed Mux playback remains independent. This slice supplies no arbitrary administrator binding override. The owned fixture adapter uses an opaque run identity and refuses another store's objects.

Checked 2026-11-12: [Blob SDK reference](https://vercel.com/docs/vercel-blob/using-blob-sdk) documents conditional deletion and null for a missing object. [Consistent private reads](https://vercel.com/changelog/vercel-blob-now-supports-consistent-reads-on-private-storage) documents bypassing CDN cache. Controlled SDK-shaped adapter success establishes application behavior, not actual account capability.

## Downloads and bounded verification

Pending/blocked requests retain bytes and permit scoped original downloads throughout recovery. Dispatch blocks new grants and new starts from existing grants, without claiming physical deletion. Previously issued links also stop at their five-minute expiry; role revocation alone does not revoke them. Transfers already started may finish after dispatch/expiry. Public removal or Mux playback deletion alone never requests archive deletion.
