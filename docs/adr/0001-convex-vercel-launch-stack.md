# Use Convex and Vercel for the launch architecture

On 2026-11-11, interview answer Q95 selected a Convex backend, a frontend hosted on Vercel and Stripe for payments, correcting the earlier assumption that the existing Express/SQLite demo stack should carry into the launch design. This user-selected architecture supersedes the Q94 Express/SQLite preview-harness choice; the replacement harness and detailed service boundaries remain to be designed against Convex. Existing demo code is historical implementation evidence, not the target architecture, and this decision authorizes documentation changes only.

Q98 selects private Vercel Blob for original videos and Mux for processed streaming, with Convex managing permissions and records; see [ADR-0002](0002-preserve-originals-in-private-blob-with-mux-playback.md). In Q96 the user confirmed that user-feedback tools, usage analytics and similar product-improvement tools are deferred until after initial release; payment confirmation, video-processing updates and advertising controls remain required for their launch features.

Q97 requested an explanation of original preservation before the Q98 storage selection. The existing REQ-138 upload allowance of 5,000,000,000 video bytes remains unchanged under the selected architecture.

The [Q97 provider investigation](../provider-research-adoption-is-launch.md#q97-original-video-preservation-investigation--2026-11-11) informed the Q98 selection of private Vercel Blob for exact originals alongside Mux playback. Provider facts and design inferences are distinguished there. Q100 permits original downloads by the uploading creator, the campaign's manager and authorized platform administrators; Q101 retains originals without automatic expiry after campaign completion or withdrawal, with explicit administrator action required for deletion. Q102 blocks deletion while an ad is active/publishing and requires confirmation/auditing; Q103 adds a 30-day recovery window before permanent removal. See ADR-0002 for the accepted lifecycle.

In Q99 the user confirmed "Keep clerk for all auth issues that apply to clerk." Clerk remains the application's authentication provider for supported identity, sign-in, invitation, session and recovery flows. Convex verifies authenticated identity and enforces current role, nonprofit/campaign and resource permissions; the provider choice does not establish those permissions or prove the outstanding O-07 behavior. Public viewing and donating remain account-free. No provider-dashboard login or account setup was requested by this clarification.

Q104 confirmed the consolidated architecture and video policies with "Yes that sounds good." Shared understanding for this architecture correction is complete. The confirmation does not authorize implementation, account setup, publication or deployment, and does not validate a replacement Convex harness or provider capability.

Q105–Q106 subsequently clarified advisory preview saves and confirmed the replacement local Convex verification design. The later explicit implementation request authorized this bounded local preview; its [run guide](../ALLOCATION-PREVIEW.md) and [executed evidence](../allocation-preview-verification.md) record the result. Earlier statements that the harness remains undesigned/unvalidated describe the Q95–Q104 checkpoint. Provider/real-Clerk/safety/full-production gates remain open; neither this ADR nor the local preview certifies them.
