# Invited creator access (T02)

The launch workspace supports **Creator invitations** for scoped managers and `?workspace=creator` for invited creators. The default workspace remains the single adoption.is manager workspace. `?workspace=public` opens an account-free link to adoption.is viewing/donation; later public campaign/ad/donation implementation remains T05. No campaign selector is introduced.

Production uses the existing Clerk/Convex integration described in [CAMPAIGN-SETUP.md](CAMPAIGN-SETUP.md). Configure Clerk's supported email-link sign-in, invitation/signup and recovery options in the applicable instance. `SignIn` provides authentication/recovery; `UserButton` provides account/session management and sign-out. The access-denial screen links back to Clerk session management. There is no application password reset, recovery token or browser-authorized role.

The signed Convex identity must contain the invited email and a boolean verified-email claim. Convex OIDC exposes `emailVerified`; custom-JWT integrations retain `email_verified`. False, missing and string claims fail closed. Application arguments cannot supply identity. The first participation acceptance atomically binds the invitation to the Clerk subject; another subject cannot reuse that email-bound invitation afterwards. Current invitation and bound creator membership must both remain active on every protected operation, including exact retries. Invitation IDs and public Clerk metadata never grant application access.

Clerk owns the invitation email/token. `creatorAccess:invite` journals the scoped application invitation after campaign rules lock. `clerkInvitations:dispatch` sends it through Clerk's Backend API using server-only `CLERK_SECRET_KEY` and a fixed HTTPS `CLERK_CREATOR_REDIRECT_URL`. Neither value is accepted from a browser; no secret belongs in Vite configuration. Clerk `ignore_existing` supports inviting an already registered email; the application's dispatch journal prevents repeat creates for an uncertain outcome. No instance or account is provisioned by this change.

A transaction records dispatch before the external call. Confirmed, failed and uncertain outcomes remain visible in the manager workspace. Exact/concurrent retries of uncertain calls look up the email plus the saved invitation's exact Clerk metadata marker rather than repeat a create/revoke POST. Missing, ambiguous, malformed and unavailable lookup evidence remains uncertain and blocks creator access. The manager can retry reconciliation after reload. Local revocation immediately denies application access, independently of provider availability. Clerk revocation of an already accepted/expired invitation needs no further token invalidation; current application membership remains revoked. This does not assert global Clerk session termination. Permission is checked before dispatch and before recording the result; if manager permission changes during the call, the journal remains unresolved for an authorized manager/administrator to reconcile.

## Actual participation terms are a release gate

No actual legal agreement was supplied with this ticket. Production signup and submission therefore remain blocked. A trusted operator must supply the actual applicable, approved `participationTerms` record for the same campaign/nonprofit before enabling participation. Its version, title, full text, approver and approval time are required; `synthetic` must be false for production. No public API authors or substitutes legal text. This provisioning and legal approval are separate work requiring actual approved content.

The agreement must cover commission, prizes, score, cutoffs, refunds and creative use, alongside the applicable campaign rules and other creator legal matters. It must preserve creator ownership, confirm permission to authorize included content, grant public display and campaign advertising permission without additional approval per submission or placement, end new advertising use on withdrawal/completion, and preserve private records explaining results/payments. These are approval requirements, not a substitute legal agreement.

`creatorAccess:accept` requires explicit confirmation of the currently displayed terms ID/version and records the creator subject, invitation, version, acceptance time, operation ID, source and an immutable snapshot of the full terms in the same transaction as identity binding and membership. Concurrent or response-loss retries return the one acceptance without another audit event. Changed versions cannot overwrite it. Historical acceptance remains available for private viewing. `creatorAccess:submissionAccess` fails closed unless current applicable terms and acceptance exist; submission intake calls the same server-side participant gate. [Photo intake and review](PHOTO-SUBMISSIONS.md) is T03; video intake remains T04.

Creator-private earnings/payment setup records are scoped by campaign, nonprofit and bound creator. Collection queries return only minimal owned projections; direct record requests reject foreign IDs. Manager invitation/audit projections require current manager/administrator scope. Public campaign metadata contains only name/slug and needs no authentication. Future earnings/payment producers remain T03/T17; the T02 schema and controlled records prove their privacy boundary without manufacturing financial balances.

## Bounded verification

`npm run dev:launch` copies fixture functions into a run-owned local Convex deployment. Its synthetic Clerk contract server uses no real credential, sends no email and creates no external account. Its localhost adapter URL is accepted only when the campaign's fixture-run ID matches the deployment's run ID. Production-scoped campaigns reject this adapter. Synthetic agreement fixtures are explicitly labelled **not legal terms** and require that same owned-run match; removing fixture scope blocks them even after a prior synthetic acceptance. Fixture control routes exist only in the development runner, never in the compiled application.

Run `npm run check`, `npm run build:launch`, `npm run test:launch:planner`, `npm run test:launch:backend` and `npm run test:launch:browser`. Backend files run serially on Windows. T02 tests use authenticated public Convex operations for manager/creator permissions, forwarding, verified claims, immutable acceptance/audit, concurrent retries, restart durability, private records, provider confirmed/failure/unknown reconciliation and synthetic/production separation. Browser tests cover desktop/mobile failed dispatch, missing terms, explicit acceptance, reopening, forwarding denial, revocation and public entry. Evidence is recorded in `.codex/ralph/t02-report.md` with redacted logs and screenshots.

These results do not prove actual Clerk email delivery, token expiry/replay, supported recovery, identity edge cases or sole-manager recovery. T38 retains those real-instance gates; actual applicable legal terms and deployment configuration also remain prerequisites to production signup.
