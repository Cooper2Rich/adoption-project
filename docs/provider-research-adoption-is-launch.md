### Verified provider facts

- Mux explicitly does not retain the uploaded original in its exact form. Its downloadable master is an equivalent-quality MP4; the temporary master URL lasts 24 hours and can be regenerated. A master is not an exact-original archive. Sources: [Mux video files](https://www.mux.com/docs/core/stream-video-files), [master downloads](https://www.mux.com/docs/guides/download-for-offline-editing).
- Convex direct file uploads have a two-minute request timeout and upload URLs expire after one hour. Standard download URLs do not automatically expire; authenticated HTTP-action serving is capped at 100 MiB. File metadata includes a SHA-256 digest. Sources: [uploads](https://docs.convex.dev/file-storage/upload-files), [serving](https://docs.convex.dev/file-storage/serve-files), [metadata](https://docs.convex.dev/file-storage/file-metadata).
- Vercel Blob supports private stores, multipart uploads and files up to 5 TB. Signed URLs allow temporary private GET access, and scoped presigned multipart uploads avoid routing file bodies through application functions. Sources: [limits](https://vercel.com/docs/vercel-blob/usage-and-pricing), [private storage](https://vercel.com/docs/vercel-blob/private-storage), [signed URLs](https://vercel.com/docs/vercel-blob/vercel-signed-urls).
- Mux accepts a source URL to ingest a video. Source access and playback authorization are separate: a private original can feed Mux through temporary authorized access. Sources: [asset creation](https://www.mux.com/docs/api-reference/video/assets/create-asset), [signed playback](https://www.mux.com/docs/guides/secure-video-playback).

### Flow adopted in Q98; implementation verification pending

Q98 adopts private Vercel Blob for unchanged source files, Mux for processed playback, and Convex for permissions, media records and processing state. Convex's two-minute upload window makes its native direct-upload path a poor fit for reliably accepting the already-agreed 5,000,000,000-byte maximum across ordinary client connections; this is an engineering inference, not a Convex file-size prohibition.

1. Authorize an upload against the creator and campaign in Convex; reserve a unique media record/object path.
2. Grant a scoped temporary upload and transfer the original bytes directly from the browser to private storage using multipart upload. Do not transcode or overwrite that source object.
3. Verify completion and actual file properties before acceptance. Record owner, competition entry/revision, object identifier, original filename, byte length, checksum and validation state in Convex. Preserve REQ-138's existing size/codec/duration/photo rules.
4. Give Mux a temporary source-read URL and store the resulting asset/playback identifiers on the media record. Verified provider events update processing state. URL expiry, retry and duplicate-event handling require implementation verification.
5. Serve website playback through Mux. Separately authorize original-file downloads and issue fresh expiring storage URLs. Preserve originals independently of Mux asset deletion and make each accepted replacement a separately identified source revision.

**Integrity recommendation, not provider guarantee:** retain SHA-256 and independently compare uploaded and stored bytes before declaring an original verified. Do not assume a Blob ETag is a SHA-256 digest. Large-file checksum/validation work must have a feasible execution design; do not buffer a 5 GB video in a normal application request.

**Trade-offs and remaining details:** storage plus Mux processing/playback incurs separate usage. Q100–Q103 settle download roles, indefinite retention, confirmed/audited administrator deletion only when inactive and a 30-day recovery window. Storage continues during that window. Actual multipart/Mux-ingestion behavior, large-file integrity verification and purge/restore concurrency require engineering validation. No numerical cost estimate or account capability is asserted. No provider accounts, uploads or test-mode operations were used.

### Deletion and recovery investigation — 2026-11-11

- Vercel documents physical Blob deletion as permanent and irreversible. No native trash/version-history restoration guarantee is established here. [Deletion documentation](https://vercel.com/docs/vercel-blob/manage-blob-storage#5-delete-blobs).
- Convex supports durable future scheduling and cancellation. A recoverable trash period can therefore be designed by marking a record deleted, retaining its Blob temporarily, and deleting physical bytes only after a confirmed retention deadline. Restore/purge races, external-call uncertainty and retries require implementation verification; this is an application design inference, not native Blob undelete. Q103 subsequently accepted a 30-day period. [Convex scheduling](https://docs.convex.dev/scheduling/scheduled-functions).
- A Convex deletion marker can deny new source URLs but does not itself invalidate previously issued signed URLs. Treat existing links as usable until expiry while the object exists; no per-link revocation guarantee was established. Short expiries and any stricter delivery design require verification. [Vercel signed URLs](https://vercel.com/docs/vercel-blob/vercel-signed-urls).
- Q102 subsequently accepted active/publishing deletion safeguards, explicit confirmation and audit retention; Q103 accepted the application-managed 30-day recovery window. These are selected policies, not implemented behavior. No separate backup/restore implementation or guaranteed protection against provider loss follows from indefinite retention.

## O-02: Stripe fundraising and payments

### Verified documentation

- Stripe distinguishes `checkout.session.completed` from `checkout.session.async_payment_succeeded` and `checkout.session.async_payment_failed` for delayed payment methods. A browser success redirect is not a reliable fulfillment signal; use server-side events and verify the relevant payment state. See [Checkout payment events](https://docs.stripe.com/payments/existing-customers?platform=web&ui=stripe-hosted) and [Stripe event types](https://docs.stripe.com/api/events/retrieve).
- Stripe supports full and partial refunds after successful payment; refunds can be pending or fail depending on payment method and balance. Refunds draw on available, not pending, Stripe balance. A refund request is therefore not proof of a completed refund. See [refunds](https://docs.stripe.com/refunds).
- Stripe's [separate charges and transfers](https://docs.stripe.com/connect/separate-charges-and-transfers) describes one possible Connect model: charges on a platform account and transfers to connected accounts. It does not establish that this campaign or its beneficiary qualifies for that model. Stripe's [payout API](https://docs.stripe.com/api/payouts/create) sends an account's funds to its own bank account, requires sufficient balance, and initially creates a pending payout; a Connect transfer and a bank payout are distinct operations. A local prize-fund allocation alone is neither.
- Connect [capability requirements](https://docs.stripe.com/api/capabilities/update) can delay activation and expose outstanding requirements. This does not establish what each creator must supply, their eligibility, or when their bank payout has settled. See also [Stripe-hosted onboarding](https://docs.stripe.com/connect/hosted-onboarding).
- Stripe's [idempotency documentation](https://docs.stripe.com/api/idempotent_requests) says v1 keys may be pruned after at least 24 hours; a reused pruned key creates a new request, and a cached first result can include a 500. [Webhooks](https://docs.stripe.com/webhooks) can be retried, duplicated and delivered out of order. Durable obligation records, reconciliation and verified signatures remain necessary; a key alone cannot prove lifetime at-most-once payments.

### Implications, assumptions and unknowns

- **Open timestamp mapping:** identify a Stripe-authoritative successful-payment instant for each enabled payment method, capture model and API version. Object creation time, event receipt time, and fund availability are not proven equivalent to successful-payment time. Validate delayed success across the Chicago period boundary and replay/reorder scenarios; do not silently substitute `created` or a webhook arrival time.
- Establish stable correlation from each tracked fundraising link through Checkout, PaymentIntent, charge and confirmed/refunded amounts, including duplicate and partial refunds, late updates, failures and disputes. Verify signed events and reconcile authoritative provider records. The exact state and timestamp that satisfies the product's confirmed-refund rule is still unvalidated.
- Determine beneficiary, merchant of record, ownership and custody of funds, permissible Connect account types and regional restrictions, fees and negative-balance responsibilities with Stripe and appropriate financial/legal review. Obtain account-specific confirmation before adopting a design. Confirm that available balance, currency and reserves support the scheduled amount while protecting creator earnings and advertising allocations; Stripe balance alone does not encode the application's reservations.
- Establish whether prize replenishment means an internal allocation or an actual supported movement between specifically identified accounts, and how each is evidenced. Test onboarding, requirements changes, restricted recipient, transfer and payout pending/failure/settlement, shortage and retry behavior. Keep unresolved payments reserved and do not infer payment settlement from transfer creation. Product policy does not authorize automatic recovery from a creator's bank or reversal of already-paid prizes.

## O-07: Clerk access and recovery

### Verified documentation

- Clerk [application invitations](https://clerk.com/docs/guides/users/inviting) send a unique link that automatically verifies the invited email during signup; invitations normally expire after a month, after which signup falls back to the normal flow without automatic verification. Invitations alone do not restrict application access; Clerk points to invite-only access mode. Possession of an invitation link can enable signup with its preverified address, so forwarded-link denial is not established by email matching alone.
- Clerk [revocation](https://clerk.com/docs/reference/backend/invitations/revoke-invitation) makes a revoked invitation link unusable but does not itself prohibit a normal signup. This is distinct from revoking access of an already authenticated creator. The application must enforce the PRD's server-side authorization and current creator status for protected operations.
- Clerk [email sign-in links](https://clerk.com/docs/guides/configure/auth-strategies/sign-up-sign-in-options) expire after 10 minutes, separate from application-invitation expiry. [Same device and browser protection](https://clerk.com/docs/guides/secure/best-practices/protect-email-links) is enabled by default and affects sign-in/signup email verification links; do not assume it also makes the separate invitation ticket non-transferable. Link replay and accepted-invitation reuse behavior are not established by these sources.
- If MFA is enabled, Clerk documents single-use backup codes and, where configured, passkey recovery. If all factors and backup codes are lost, [MFA recovery](https://clerk.com/docs/guides/secure/mfa-recovery) requires a Dashboard or Backend API reset, and the reset does not itself revoke sessions. Clerk leaves identity-verification criteria for an MFA reset to the application/operator. [Lockout](https://clerk.com/docs/guides/protect/user-lockout) can require an administrator unlock depending on configuration. These do not establish recovery from loss of the Clerk Dashboard account or the sole manager's mailbox.

### Remaining validation

Use an isolated Clerk instance to test invited identity and verified-email association, forwarded invitation before acceptance, existing accounts, expiry and replay, revoked invitation, revoked creator with an active session, direct server requests, email changes, manager access, lost factors and recovery. Identify who can access the Clerk Dashboard and its provider-supported recovery route if the sole manager loses their mailbox, MFA or dashboard access. Do not invent an internal recovery system. A forwarded invitation that grants the bearer a preverified identity would conflict with REQ-105's forwarded-link denial; establish the actual behavior and mitigation before treating that criterion as feasible.
