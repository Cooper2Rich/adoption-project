# Launch readiness registry

`readiness:read` is scoped and read-only. `readiness:evaluate` and `readiness:checkPaidActivation` are the intended signed manager/administrator operations. Opening the shared Launch readiness workspace invokes evaluation. Each required unmet component of PG-01–PG-06 atomically writes a stable blocker and calls T08 `recordTrustedIncident`; repeated evaluations update the stream without duplicate detection mail. Recovery resolves that episode with one recovery notice. The current designated operator/contact route and T08 durable dispatch/retry/unknown-send fences apply. Email failure never clears readiness.

Paid activation is **unavailable**: there is no production admission/advertising dispatcher in this baseline. Checks return denied and persist detection, with no reservation, spending or activated state. `guardPaidActivation` is the reusable transactional seam: every future paid writer must call it inside its own mutation, recheck current resource/configuration/evidence/authority revisions, return denial before side effects and avoid throwing after detection (Convex rolls back mutation writes). A stale expected revision remains denied. Do not turn this advisory check result into a reusable dispatch token. The existing `reservations:reserve` remains an explicitly fixture-only S1 primitive, with its own bounded regression coverage.

Platform administrators can use `readiness:configureScope` as an integration seam to bind opaque account digests and an explicit selected-provider scope (empty means unconfigured). This sets scope only; it approves no gate. Optimistic `expectedVersion` prevents stale/concurrent overwrite. Unselected provider components are visibly not applicable; missing/all-empty selection never waives advertising gates. Actual onboarding belongs to its provider slices. No normal setup flow asks users to paste validator JSON or invent provider facts.

`recordValidatedReadiness` is a backend-only, nonregistered validation/provenance seam. Future trusted validators must validate actual provider or production facts before calling it under the component's fixed validator identity. The seam requires the exact nonprofit, campaign, account digest and current configuration/settings/terms/authority/finance revision, current reviewed owner from the existing memberships/operators, digest, monotonically ordered sequence/time, expiration and explicit outcome. Reserves/freshness/release facts and verified required/available funding have separate typed inputs, without numeric defaults. A verified balance cannot certify an eligibility contract. Insufficient but valid funding evidence persists as a blocker. PG-05 depends on current PG-01–PG-03 evidence. Expiration schedules a trusted reevaluation; every direct paid check independently revalidates expiry and owner authority. Missing unvalidated production inputs stay held. No production adapter calls the seam yet; environment variables, evidence URLs, user assent, closed research and passing fixtures cannot approve it.

Proof history is append-only. The manager/admin projection includes safe opaque digests, reviewed owners, actor/source/time/version, scoped revision and actual unmet reason. Trusted adapters must supply redacted opaque references and identity subjects, never credentials or raw provider payloads. Denied guests, creators, other nonprofits and revoked roles cannot read the registry or call its application operations. The test-only fixture is copied solely into the matching anonymous local deployment, labels evidence unvalidated, cannot switch to production provenance and independently cannot authorize paid activation. Re-tagged fixture evidence is rejected by projection as well as ingestion.

PG-01/PG-02 collection eligibility and route evidence are separate from PG-03 paid advertising contracts. Creator intake/review and approved public waiting creatives retain their current identity/terms/media checks while paid gates fail. Public advertising contribution checkout remains unavailable until its separate integration; this registry creates no checkout, alternative collection route or substitute business model.

Required actual gates remain external: Stripe eligibility #20, funding/refund/return/read contracts #21, selected Meta/TikTok contracts #12, real Clerk proof T38, actual safety parameters #22, and production/media/email/consolidated acceptance T39/T40. Controlled proof demonstrates registry transitions only. Later production writers and monitors own their exact detection sampling and actual provider validation; this registry does not claim instantaneous external monitoring or whole-launch completion.

Verification: `node --test tests/launch/readiness.test.ts` uses actual isolated Convex, signed application operations, owned HTTP email transport, two sessions, expiry, failure/unknown delivery, concurrency and real process restart. `npx playwright test --config playwright.launch.config.ts tests/launch-browser/readiness.spec.ts` exercises the shared desktop/mobile screen and incident/recovery journey. The full launch suites include both.

Production media/email/behavior/launch-review proofs additionally bind the independent current build/environment target. `recordCurrentReleaseTarget` is a nonregistered trusted-controller seam with scoped environment/build digests and ordered sequence/time. It persists a target change and reevaluates blockers in the same mutation. Missing targets hold acceptance; changed targets invalidate old acceptance without invalidating unrelated provider contracts. No production controller is wired yet. Its future deployment owner must update the trusted target for every build/environment change; database metadata alone does not detect a real redeploy. The fixture simulates this context only in its isolated owned deployment, and never establishes release approval.

An explicitly reviewed zero prize obligation is accepted only with trusted current evidence and existing locked rules whose daily prizes, weekly prizes and replenishment commitments are all explicitly zero. Missing rules/evidence or zero against positive locked commitments remains held/rejected. This is not a numeric default; the full-run baseline commitment remains strictly positive.

Prelaunch scopes may contain only Stripe bindings. Omitted or explicitly empty account bindings stay unknown, and evidence for an unbound account is rejected. An empty advertising-provider selection is unconfigured: all Meta/TikTok components remain required and held even if account hashes or proof records exist. Current reviewed PG-01/PG-02 collection/refund/return prerequisites can independently show controlled eligibility without advertising or media setup; checkout stays unavailable. Nonempty explicit selections determine only the selected advertising components' applicability.

Verified safe-integer negative availability is retained as an explicit coverage deficit, never clamped to zero or mislabeled unknown. Missing, nonfinite or unsafe values are rejected as invalid evidence; required obligations cannot be negative, and full-run baseline obligations stay positive.
