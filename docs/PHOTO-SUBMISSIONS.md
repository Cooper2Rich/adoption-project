# Photo submissions (T03)

The invited, terms-accepted creator workspace accepts JPEG/PNG photos. Manager **Photo review** shows exact original files and permits revision requests, rejection with a reason, and approval. Staff have no creative mutation or transformation operation. Approval changes application eligibility only; it makes no external advertising call or reservation.

Each file permits 1–100,000,000 bytes inclusive, with 1–10 distinct photos and at most 1,000,000,000 photo bytes per entry. The total ceiling is also implied by the count and per-file limits. Browser hints and token restrictions supplement authoritative validation: the server reads the completed private object, counts actual bytes, verifies its signature and claimed format, decodes the still image, and hashes the unmodified stored bytes. Invalid or incomplete uploads never become submittable. Acceptance does not guarantee a platform will accept or place the creative. No resize, recompression or reformatting occurs.

## Production path and configuration

The launch frontend uses `/api/photos` (the Vercel Node function in `api/photos.mjs`). Configure that function's server-only `CONVEX_URL`, a private store's `BLOB_READ_WRITE_TOKEN`, and a random `PHOTO_RECEIPT_SECRET` of at least 32 characters. Set that same receipt secret in the corresponding Convex deployment. Never place either secret in Vite configuration. Actual approved participation terms, Clerk and Convex setup are still required; missing applicable terms block production submission. This change provisions no provider or deployment.

`photos:reserve` checks the current T02 participant gate and reserves an owner-, campaign- and acceptance-bound immutable pathname. The authenticated token route checks the current participant again before the Blob SDK issues an exact-path capability valid for at most the reservation's ten-minute window. Its allowed content type and 100,000,000-byte maximum are explicit; overwrite and random suffix are disabled. The browser uploads multipart directly to private Blob, avoiding Vercel Functions' 4.5 MB upload-body ceiling. Arbitrary browser paths, completion notifications and browser-supplied size/type cannot finalize an upload.

The authenticated verification route reads only the reserved private pathname, validates the actual bytes and signs a short-lived integrity receipt. Convex verifies the receipt, current participant, acceptance and reservation before recording the immutable size/type/hash and verification time. No browser operation can issue receipts. Exact verification retries return the existing matching verification; changed bytes or changed operation contents conflict.

`photos:submit` atomically links verified uploads, title, description, creator and accepted agreement. Versions and actor/source/time/operation audit remain identifiable. Concurrent edits require the observed version. Before first approval, corrections retain the entry and reserved tracked fundraising path. Once an entry has ever been approved, changed ordered photo content (verified hashes/type/size) creates a distinct pending entry and path. Reuploading identical original bytes or editing title/description keeps the original entry. Every submitted revision requires review. A replacement copies no approval, metric or earnings record, and preserves the original entry/history. The reserved `/fundraise/<entry-id>` path is data for T05's public fundraising route; it does not authenticate anyone or originate fundraising credit.

Authenticated resource requests check current uploader or scoped manager/administrator permission through Convex and stream the original private bytes with `private, no-store` and `nosniff`. No permanent public Blob URL or bearer download grant is exposed. This applies even after approval and to historical versions. Historical reads retain current invitation/membership checks independently of new-submission terms availability, so a missing applicable agreement blocks new intake while preserving access to saved history. `photos:publicEntry` returns only the current approved entry's public metadata; pending/rejected/revision records deny public direct calls. T05 owns the public display/fundraising flow. Private creator projections never return another creator's submissions or audit.

## Bounded verification and remaining gates

The existing owned local Convex runner copies only run-owned fixture controls. It installs an ephemeral receipt secret in its own deployment and uses a persistent disk byte store behind the same API service. Its server checks the campaign's fixture-run identity on every byte/token/verification request. The production API has no local write route or fixture identity. Synthetic participation terms are clearly marked **not legal terms** and cannot authorize production participation.

`npm run test:launch:backend` runs the actual Convex/public-operation tests serially. T03 writes and verifies ten actual valid 100,000,000-byte PNGs, submits the full 1,000,000,000-byte entry, and retrieves/hash-checks a complete exact-limit file. It exercises JPEG/PNG decoding, malformed/truncated/type/size errors, count overflow, immutable bytes, forged receipts, privacy/revocation, terms/synthetic-scope separation, retry/concurrent edits, revisions/approval, identity rules and restart durability. A separate official SDK token test uses an explicitly synthetic local signing key without any provider call. `npm run test:launch:browser` drives actual desktop/mobile upload, error, correction, rejection, approval, replacement and revoked-state journeys. Evidence lives under `.codex/ralph/t03-*`.

These checks establish the bounded application and controlled adapter behavior. They do not establish real Blob account grants, private-store setup, multipart delivery/retry, cross-region byte transfer, throughput/timeouts, real Clerk behavior or production configuration. T39 retains actual media-provider evidence and T38 actual Clerk evidence. Actual approved legal terms remain missing. Paid launch is not certified.
